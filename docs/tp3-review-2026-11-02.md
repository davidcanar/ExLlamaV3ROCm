# TP=3 (3 x Strix Halo, OdinLink mesh) — review of 2026-11-02

Model: DeepSeek-V4.1-Flash 3.5bpw (`model-3.5bpw` + `engram-src-1017`), 512K cache, DSpark on.
Profiler: `perf/tp3/run_prof3.sh` + `perf/tp3/tp3_prof.py` (TP=3 port of `perf/tp_prof.py`;
probes the cable map itself). Raw data: `perf/tp3/prof3.jsonl`, `perf/tp3/*-rank0.log`.

## 1. Why TP=3 hung after this morning's driver reload (fixed)

`ODL_RCCL_PEERS` is a per-boot map and Box2's devices flipped at the 10:42 `odl_tb5` reload:

| box | dev0 -> | dev1 -> | correct map | `tp3_worker.sh` had |
|---|---|---|---|---|
| Box1 | Box3 | Box2 | `10.0.2.2=1,10.0.2.3=0` | same |
| Box2 | Box3 | Box1 | `10.0.2.1=1,10.0.2.3=0` | `10.0.2.1=0,10.0.2.3=1` (stale) |
| Box3 | Box1 | Box2 | `10.0.2.1=0,10.0.2.2=1` | same |

With a stale map the plugin opens a connection on the cable to the *other* peer; its hello lands on
that box's control stream (id 20 on every device) and is accepted there because listener ids are
per-process counters that collide across boxes. Connections cross, the per-pair stream counts go
asymmetric (2 vs 4, the signature in the runbook) and the world-3 warmup / first big collective
hangs. That is the "rccl3 regression" and very likely the 1M-context hang too.

Fix: `tools/ds41/odl_peer_probe.py` pings every cable from all three boxes at once and prints each
box's map; `tp3_start.sh` now runs it on every start and hands each rank its own
`ODL_RCCL_PEERS` (`./tp3_start.sh probe` prints it). The old launcher also forwarded one shared
`ODL_RCCL_PEERS` to both workers when it was set in the shell, which can never be right for both.

## 2. Decode: odl_ar3 — mesh all-reduce over OdinLink (new, default on)

All 80 decode all-reduces per token went through 3-rank RCCL over the net plugin (ring = 4 network
steps, then a host stream sync after every op). `odl_ar3` (`~/exl3ds4/odl_ar3`, Python side
`model_tp_odl.OdlAllReduceMesh`) sends each rank's partial straight to both peers over their own
cables and sums all three in fixed rank order: one hop, both cable directions busy, stream-ordered
(no host sync), bit-identical on every rank (verified). Peers are discovered by a ping on each cable
(no device map needed). Lost messages are recovered (header with the round number, NACK on a gap or
timeout, resend from the send slot, which provably cannot have been reused yet).

Microbenchmark (`perf/tp3/ar3_bench.sh`, per all-reduce, as the backend uses it):

| payload | RCCL + host sync | odl_ar3 |
|---|---|---|
| 10 KB (1 decode row) | 170–179 us | 40–42 us |
| 20 KB | 225–232 us | 50 us |
| 60 KB (6-row verify) | 288–338 us | 90–94 us |

Model, 3.5bpw, greedy (unprofiled step/round times):

| | baseline (RCCL) | odl_ar3 |
|---|---|---|
| 2K plain decode | 57.6 ms/token (17.2 tok/s) | 46.8–47.7 ms (21.0–21.4 tok/s) |
| 2K DSpark | 135 ms/round, 23.0 tok/s | 92 ms/round, 30.2 tok/s |
| 32K plain decode | 62.3 ms (16.1 tok/s) | not measured (runs blocked, see 4.) |
| 32K DSpark | 125 ms/round, 26.4 tok/s | not measured |

Greedy plain output is byte-identical to the RCCL run (same hash in 3 runs). DSpark output shares the
first 206 characters and then takes the other side of a near-tie ("summarize each concisely." vs
"summarize each."): odl_ar3 rounds the 3-way sum once instead of after each ring step — the same
float sensitivity already seen run-to-run on TP=2.

Loss recovery, tested by injection (`ODL3_TEST_DROP=37 ODL3_TEST_DROP_RANK=0`: rank 0 skips the first
transmission of every 37th round): both peers caught all 50 gaps, rank 0 resent 101 rounds, one
spurious duplicate was dropped, every result stayed bit-identical and exact. One real CRC loss on
stream 243 (12:45:23, Box2) was recovered the same way. Counters are printed at shutdown
("odl_ar3: rankN recovered losses: ...").

Rollback: `EXL3_TP_ODL_AR3=0` (all ranks; the setup is collective, so a box with it off makes every
rank fall back to RCCL instead of hanging).

## 3. Prefill: where the time goes (per 2048-token chunk, 8K prompt, rank 0, synced profile)

| op | s/chunk | share |
|---|---|---|
| all-reduce (RCCL, 80 x 20 MiB bf16) | 1.70 | 29% |
| sparse attention (dsa_attn) | 1.22 | 21% |
| MoE (routed experts) | 1.07 | 19% |
| Engram (2 layers, host lookups) | 0.69–0.84 | 12–15% |
| other linears | 0.60 | 10% |
| hyper-connections | 0.36 | 6% |

- RCCL moves a 20 MiB all-reduce in 14.5 ms (1.45 GB/s algbw, ~1.9 GB/s per link direction): close
  to what the 20 Gbps links give. A mesh reduce-scatter + all-gather over the stream API (written,
  `EXL3_TP_ODL_AR3_BIG=1`, off) was correct but slower (1 sender thread per cable ~1 GB/s).
  The biggest prefill lever is link speed: every cable trains at USB4 Gen2 (10 Gb/s x 2 = 20 Gbps).
  Certified 40 Gbps USB4/TB4 cables (passive <= 0.8 m or active) should train at 20 Gb/s x 2.
- Every TP=3 layer has one rank with 32 heads and two with 16 (pow2 split 4/2/2 groups; the heavy
  rank rotates). The attention phase of every layer runs at the 32-head speed; a 24/24/16 split needs
  attention kernels that tile 24 heads (today HP / BLOCK_H must be powers of two dividing the heads).
- Engram is replicated on all ranks and gathers rows from the 2 x 101 GB tables on NVMe with host
  work in the critical path (decode too: ~3.6 ms/token). Splitting its heads over the ranks (each
  rank gathers 1/3, one extra all-reduce) or prefetching layer 14's rows at pass start would help.

## 4. Reliability findings (not fixed here)

1. **The OdinLink DMA path loses frames under load and nothing retransmits them.** Seen today:
   Box2 11:50:01 (fragment gap, no CRC flag), Box2 12:06:25 (RX CRC error), Box2 + Box3 12:11:01
   (RX CRC errors) — about 1 per 10–20 M frames. The driver drops the whole message; RCCL then hangs
   until the watchdog. odl_ar3 recovers its own messages now; the RCCL plugin does not. A
   NACK/resend layer in the plugin (or driver) is needed for long prefills (1M) to be reliable.
   Box2 also runs a different kernel (7.2.13 vs 7.1.8) and had all the losses until 12:11 — worth
   aligning it and swapping/reseating its cables to localize.
2. **Intermittent RCCL stall at the first large collective.** 3 of the last 6 starts (all with odl_ar3
   initialised; the single RCCL-only start passed) stalled in the warm-up's first prefill-sized
   all-reduce with no link error logged: every rank inside the same layer-0 all-reduce, the RCCL proxy
   spinning, nearly every plugin worker idle (no transfer queued) — i.e. NCCL waiting on a connection
   it builds lazily for its first Simple-protocol op. The runbook's "rccl3_allreduce hangs since this
   morning" started before the cable map went stale, so this looks like a separate plugin
   connection-setup bug. Next step: one run with `ODL_DEBUG=1` on all ranks to capture the
   hello/grant trace of the stuck connection (plugin logs go to /tmp/odl_plugin.<pid>.log). Whether
   odl_ar3's idle polling on the same devices raises the odds is not settled (small sample).
3. **Signals/ptrace break RCCL.** The plugin's comm workers block in `STREAM_RECV`; the driver returns
   a non-restartable `-EINTR` when the wait is interrupted (e.g. `py-spy dump` without
   `--nonblocking`), the plugin marks the transfer failed and NCCL raises `ncclSystemError`. Retry on
   `-EINTR` in `do_transfer()` (recv side is safe: nothing was dequeued).
4. `tp3-rank0.log` lost every Python line when rank 0 was killed (block-buffered stdout); the new
   `tp3_start.sh` runs rank 0 with `PYTHONUNBUFFERED=1`.

## 5. Other opportunities (measured, not implemented)

- DSpark drafter: 13 ms/round on rank 0 alone (ranks 1-2 idle) = 14% of a round with odl_ar3.
- MoE expert parallelism: each token's 6 experts land unevenly on 3 ranks (expected max ~3 of 6).
  `EXL3_TP_MOE_TENSOR_SPLIT=1` (new, off, untested) loads experts split by width instead.
- Prefill chunk (`EXL3_TP_SPAN`, 2048): 4096 rows halves the per-chunk fixed costs if memory allows.
- `TCP_NODELAY` is now set on the control sockets (no effect on plain decode; it removes a Nagle /
  delayed-ACK stall risk between the DSpark accept and round frames).
